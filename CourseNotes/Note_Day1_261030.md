## 實作重點與 Code Review（程式碼審查）
- **1. 明確指定專案的 Python 環境**
  - `.venv` 是專案專用的虛擬環境，讓本專案的套件與其他專案分開管理。
  - 使用 `.venv\Scripts\python.exe`，可明確指定這次使用的直譯器；單獨輸入 `python` 或 `pytest`，則取決於終端機的命令搜尋路徑。
  - `python -m pytest` 表示由指定的 Python 執行 pytest 模組，有助於避免套件安裝在一個環境、測試卻在另一個環境執行。
  - 本次確認 Python 3.14.8、pytest 9.1.1、Paramiko 5.0.0 都來自專案虛擬環境。

- **2. 分清楚匯入、測試收集與測試執行**
  - pytest 收集測試時會匯入測試模組，因此模組頂層的可執行敘述也會執行。
  - 如果直接把 `getpass()` 或連線呼叫寫在頂層，光是收集測試就可能要求輸入或建立連線。
  - 定義函式通常不會執行函式本體；目前密語輸入位於 fixture（測試前置與清理機制）函式內，所以收集時不會觸發。
  - `--collect-only` 只列出找到的測試，不進入一般測試執行流程。本次找到 1 個測試，不能據此宣告 Ubuntu 連線或 hostname 驗證成功。

- **3. 用 fixture 管理測試需要的連線**
  - `test_hostname(ssh_client)` 中的參數名稱，讓 pytest 知道測試需要 `ssh_client` fixture。
  - fixture 在 `yield client` 前取得密語並建立 SSH（Secure Shell，安全遠端連線協定）連線，再把 client 交給測試使用。
  - `scope="module"` 表示同一測試模組內使用此 fixture 的測試共用這個 fixture 實例；不是每條遠端指令都重新連線。
  - 測試主要負責下指令與驗證結果，fixture 負責前置準備與清理，讓責任較清楚。
  - 共用連線也代表測試可能互相影響；後續增加測試時要留意連線狀態與測試隔離。

- **4. 用 finally 嘗試釋放連線資源**
  - `client.connect()` 與 `yield client` 都位於 `try` 內，`client.close()` 位於 `finally`。
  - 連線成功且測試結束後，pytest 會恢復 fixture 的清理流程，關閉連線。
  - 連線拋出例外，或測試中的 assert 驗證失敗，正常的例外處理與 pytest 清理流程仍會執行 finally。
  - 清理不代表例外被吃掉；目前沒有用 except 隱藏失敗，因此失敗仍能向外傳遞。
  - finally 的保障有邊界：程式尚未進入 try、程序被強制終止，或執行永久卡住時，不能保證及時清理。

- **5. 分清楚主機驗證與使用者驗證**
  - `load_host_keys()` 載入 known_hosts，讓用戶端可核對遠端主機的公開金鑰。
  - `RejectPolicy()` 會拒絕未知主機；已有紀錄但主機金鑰不符，也會造成連線失敗。
  - 主機驗證回答「連到的是否為預期主機」；使用者私鑰驗證回答「是否允許這個使用者登入」。
  - Passphrase（私鑰保護密語）用來解鎖受保護的私鑰，與遠端帳號的登入密碼是不同概念。
  - 私鑰內容與密語不應寫入程式、課程筆記或版本控制。

- **6. 將互動輸入視為目前階段的限制**
  - `getpass()` 適合有人操作終端機時輸入密語，輸入內容通常不會顯示在畫面上。
  - 移到 fixture 只是避免收集時要求輸入；實際執行使用此 fixture 的測試時，仍需提供密語。
  - 未來加入 CI（Continuous Integration，持續整合）時，沒有操作人員可即時輸入，必須另行設計憑證取得方式。
  - 後續遠端指令執行器應由呼叫端提供驗證資料，讓執行器專注於連線、執行與清理。

- **7. 分開保留指令的輸出與結束代碼**
  - stdout（Standard Output，標準輸出）保存指令的一般輸出；stderr（Standard Error，標準錯誤）保存另一條輸出串流，常用於診斷訊息。
  - Exit Code（結束代碼）表示遠端程式如何結束；通常 0 表示成功，非零的具體意義由程式定義。
  - stderr 有內容不一定代表失敗；也不能只靠 stdout 有內容就判定成功。
  - 指令已執行並回傳 7，與驗證失敗而無法執行指令，是不同層次的結果。
  - 現有測試只需要比對 hostname，因此使用 `.strip()` 去除前後空白；通用執行器應考慮保留原始文字，避免刪除有意義的空白。

- **8. 大量輸出可能影響讀取順序**
  - 目前先呼叫 `recv_exit_status()` 等待結束代碼，再讀取 stdout 與 stderr。
  - 少量 hostname 輸出通常容易完成；但大量輸出可能塞滿通道緩衝區，使遠端程式等待用戶端讀取。
  - 若用戶端同時只等待程式結束，就可能形成雙方互等。
  - 後續執行器要在等待結束的過程中持續處理兩條輸出串流，並配合整體期限；只對調一行程式未必能完整解決。

- **9. 為不同等待階段定義逾時**
  - 建立網路連線、SSH 協定交握、使用者驗證、開啟通道與等待指令完成，是不同的等待階段。
  - `connect(timeout=10)` 不能直接解讀為整個連線與驗證流程必定在 10 秒內完成。
  - `exec_command(timeout=10)` 涉及通道開啟與讀寫等待，不能直接當成遠端指令從開始到結束的總期限。
  - 後續需要定義整體截止時間、逾時後回報方式與資源清理方式。
  - 關閉本機連線不等於保證遠端所有子程序都已停止；若需要這項保證，必須額外設計。

## 複習回饋與完成紀錄
- 第 1 題：理解收集階段不執行一般 fixture 的前置與清理；補充收集會匯入模組，因此頂層敘述仍會執行。
- 第 2 題：理解指定虛擬環境直譯器可明確選定執行環境；補充 PATH（命令搜尋路徑環境變數）與啟用狀態會影響命令解析，指定環境不等於固定套件版本。
- 第 3 題：經補答確認，SSH 身分驗證失敗會導致無法登入，目標遠端指令尚未執行，因此沒有該指令的回傳結果。
  - 身分驗證：確認使用者是否有權登入。
  - 測試結果驗證：指令執行後，用 assert 判斷輸出與結束代碼是否符合預期。
  - 若預期結束代碼為 7，實際也是 7，測試可以通過；這與登入時的身分驗證是不同概念。
